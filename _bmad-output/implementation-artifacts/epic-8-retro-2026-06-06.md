## 🏆 Éxitos y Fortalezas
1. **Sincronización Bidireccional Segura y Robusta**: El endpoint de webhook de Zafronix valida de manera fiable firmas HMAC, mitigando ataques de replay mediante una ventana de tolerancia temporal de 5 minutos dual (segundos/milisegundos).
2. **Respaldo Automatizado Eficiente**: Implementación de sincronización por ETags en el Cron Job que previene transferencias de datos innecesarias y ahorra cuota de la API al retornar `304 Not Modified`.
3. **Resiliencia en Tests de Integración**: El cliente de pruebas sandbox maneja correctamente los límites de tasa (429) de la API externa implementando reintentos basados en `Retry-After` y una política de fail-fast en retrasos largos para optimizar el feedback de desarrollo.

## 🔍 Lecciones y Resolución de Trabajo Diferido (Deferred Work)
Durante la sesión de endurecimiento de la Épica 8, se analizaron y resolvieron todos los ítems de trabajo diferidos:

1. **Recalculación de Puntos en Correcciones de Marcadores (`match.patched`)**:
   - **Problema**: El trigger original de cambio de estado de partido no recalculaba las predicciones de duelos y ligas si el partido ya había sido evaluado (`evaluated_at IS NOT NULL`).
   - **Solución**: Se actualizó el trigger `fn_resolve_challenges_on_match_status_change` para forzar la re-evaluación e invalidación idempotente en caso de correcciones, recalculando tanto los duelos de saldo de puntos como las predicciones clásicas de las ligas activas.
2. **Protección contra Eventos Fuera de Orden**:
   - **Problema**: Webhooks retrasados o entregas en desorden de la API externa de Zafronix podían clobberar (sobrescribir) datos más frescos con información obsoleta.
   - **Solución**: Se añadió la columna `external_last_sync_at` en la tabla `matches`. El webhook de la API de Next.js verifica que el timestamp del payload recibido sea estrictamente superior al último registrado para ese partido, descartando eventos antiguos en desorden.
3. **Normalización de Fases en Script de Restauración**:
   - **Problema**: El script de restauración insertaba valores crudos de fase de la API (ej: `1/8`, `1/4`), violando las restricciones del constraint CHECK `matches_stage_check`.
   - **Solución**: Se implementó una función `normalizeStage` en `restore-zafronix-data.ts` que mapea de forma segura strings de la API externa a la nomenclatura interna de fases (`last_16`, `quarter`, etc.).
4. **Timestamps en el Año 9999 y Validación de Replay**:
   - **Problema**: La heurística de conversión de timestamps segundos/milisegundos fallaba con fechas lejanas en el año 9999 usadas por el sandbox (se confundían segundos con milisegundos), causando rechazos injustificados.
   - **Solución**: Se rediseñó la verificación de la ventana de replay en `route.ts` para evaluar el timestamp de manera dual tanto bajo escala de segundos como de milisegundos contra la hora actual del servidor.
5. **Propagación de Errores y Robustez del Webhook**:
   - **Problema**: La consulta de base de datos en `findLocalMatch` ignoraba silenciosamente errores, y fallos de stream en la lectura del cuerpo del request (NextRequest `req.text()`) retornaban un código 500 genérico.
   - **Solución**: Se encapsuló la lectura del stream en un bloque `try/catch` que retorna `400 Bad Request` en caso de fallo, se propagan y registran logs de los errores de base de datos supagabase y se agregaron logs detallados de advertencia en fallas de firma HMAC.
6. **Validación Estricta Zod**:
   - **Problema**: Los esquemas del contrato de webhook de Zafronix aceptaban IDs y timestamps mal formateados.
   - **Solución**: Robustecimiento del contrato TypeScript para obligar a que los IDs no sean vacíos y los timestamps cumplan el formato `.datetime()`.
